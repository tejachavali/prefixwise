## Gemini and the OpenHands conversations: fixed

In test H, LiteLLM built no Gemini request for any conversation from `nebius/SWE-rebench-openhands-trajectories`.
The first try of this round recorded the error: `'NoneType' object has no attribute 'get'`, raised by LiteLLM's
Gemini translation on all 320 requests.

The cause was in the test's dataset loader. The dataset is stored as Parquet, which gives every tool definition
the same struct, so a parameter one tool lacks comes back on it as `null`. LiteLLM's Gemini translation fails on a
property whose schema is `null`, with that error (reproduced with 1.110.2). OpenAI, Anthropic and both Bedrock
formats pass it through. The loader now drops null-valued keys from tool schemas and counts the tools it changed
(`ff825e0`).

| | Gemini | The other four targets |
|---|---|---|
| Before the fix (the first try; its printed output, no file kept) | 0 of 320 requests translated | 300 / 300 pairs append-only |
| After (`r3-b-nebius.json`) | **300 / 300** pairs append-only, 0 untranslated | 300 / 300 each |

100 tool definitions had null keys dropped (counted over the rows read, which can include rows the test then left out).

## Live replays of real conversations, first try: no result (harness bug, fixed)

Four Open-SWE-Traces Claude Code conversations were to be replayed on real Anthropic (claude-haiku-4-5) and OpenAI
(gpt-4.1-mini), unchanged and with one change injected: 32 replays per provider (2 routes, 4 kinds, 4 conversations).
Each replay's first call (the system prompt and the task) was answered; its second, the first with a tool call in
it, was rejected. So 64 of the 128 calls were rejected, and 64 reached a model:

- Anthropic: `tool_use ids were found without tool_result blocks immediately after`.
- OpenAI: `No tool output found for function call` (Messages API route), and `An assistant message with 'tool_calls'
  must be followed by tool messages` (chat completions).

The cause was in the test's converter, not in Prefixwise or LiteLLM. Claude Code logs each content block of one
reply as its own assistant entry, and the converter kept those as separate messages, so a tool call was followed by
another assistant message instead of its result. The offline replays use a cache mock that does not check this,
which is why test H passed.

The converter now merges such entries into one turn and answers every open call before the next message
(`25465ef`). Review of that change found three more shapes a live API would reject, now handled too: the same
tool-call id in several turns (a dataset with no ids gets `call_t0` in every message), two split entries with the
same id, and an assistant entry before the first user message. A conversation that still breaks the rules is
skipped and counted (`skipped_invalid`). `hf_litellm.py selftest` checks seven such shapes, in OpenAI form and in
the Anthropic body; each fix's cases fail on the converter before it. These files are kept as a record of the
failure, not as results: `r3-live-anthropic.json`, `r3-live-openai.json`.
