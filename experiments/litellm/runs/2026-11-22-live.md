# Test G: LiteLLM's Messages API on real APIs (2026-11-22)

`live_messages.py`, run by Muse in Colab on real Anthropic and OpenAI, with Prefixwise 0.12.4 at 4a72672d
(the release code) and LiteLLM 1.110.2 (Python 3.13.18). OpenRouter and Bedrock were not run (no keys).
Each conversation: 4 turns of about 6-7k tokens (a fixed system prompt, three tools, a 220-function file),
one change injected at turn 3, a breakpoint on the system prompt and on the last message as Claude Code
sends them; streamed and not. Turn 1 should be `first_write`, turn 2 a hit, turn 3 the injected cause
(a hit when nothing changed), turn 4 a hit. Cells: cached / prompt tokens as the provider reported them.

## Whose misses: `openai_cache_probe.py` (same day, Colab, gpt-4.1-mini, LiteLLM 1.110.2, openai 2.54.0)

The same conversation sent six ways, nothing injected; cached / prompt per turn:

| how | turn 1 | turn 2 | turn 3 | turn 4 |
|---|---|---|---|---|
| A. Responses API directly, 1 s apart | 0/6135 | 6016/6158 | 0/6181 | 0/6204 |
| B. Responses API directly, 5 s apart | 0/6139 | 0/6162 | 0/6185 | 0/6208 |
| C. Responses API directly, 1 s, `prompt_cache_key` | 0/6138 | 6016/6161 | 6016/6184 | 6144/6207 |
| D. Chat Completions directly, 1 s | 0/6140 | 6016/6163 | 6016/6186 | 6016/6209 |
| E. LiteLLM Messages API, 5 s | 0/6136 | 0/6159 | 0/6182 | 0/6205 |
| F. LiteLLM Messages API, 1 s | 0/6137 | 0/6160 | 0/6183 | 0/6206 |
| F'. each body LiteLLM sent in F, replayed directly | 0/6137 | 0/6160 | 6016/6183 | 0/6206 |

LiteLLM sent `include`, `input`, `max_output_tokens`, `model` and `tools`; no field but `input` changed
between turns. So the misses are OpenAI's: the Responses API without `prompt_cache_key` mostly did not
read its cache for this conversation, called directly or through LiteLLM (A, B, F'), while Chat
Completions (D) and the Responses API with `prompt_cache_key` (C) read it on every turn. Prefixwise's
`routing_miss` and its fix (a stable `prompt_cache_key`) were right. One conversation per line: a small
sample, consistent with the 38 of 40 above.

For LiteLLM: when it sends a `/v1/messages` call on to an OpenAI model through the Responses API, it sets
no `prompt_cache_key`, though it has a stable session (Claude Code's `x-claude-code-session-id`, which
the proxy server already makes `litellm_session_id`). Passing it would likely let OpenAI read its cache.

> **Correction (2026-11-26).** LiteLLM does set `prompt_cache_key` on this route when `metadata.user_id` is the JSON string Claude Code sends, keyed on its `session_id` (`prompt_cache_key_from_user_id`, in 1.108.3 and 1.110.2). These test calls did not carry that JSON (here: the session only in the `x-claude-code-session-id` header), so LiteLLM had nothing to key on. The misses measured are OpenAI's behaviour without a key; they do not show that real Claude Code, which sends the JSON, goes without one. See finding 6 in `../README.md`.
